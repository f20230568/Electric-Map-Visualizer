How the large board is drawn
  1. Random division into sub-forests. The trees are shuffled (with the partition seed) and divided into
    k = ceil(vertices / vertices-per-board) boards
    By vertices: trees are taken largest first (equal sizes in random order) and each goes to the board that has the fewest vertices so far, so all boards get almost the same number of vertices. By trees: the shuffled trees are dealt round-robin, so all boards get the same number of trees (±1). A tree is never cut.
  2. One board per sub-forest, same algorithm. Every sub-forest is drawn exactly as on the single-board page: octilinear traces on a grid, the gender rule (female: last segment horizontal / vertical, male: diagonal), generation-by-generation routing with the bus bonus, look-ahead and rip-up and reroute, the squeeze pass, and footprint packing of the trees of that board.
  3. Boards in a grid. The boards are placed side by side in rows and stacked row on row. Each column is as wide as its widest board and each row as high as its highest board; every board sits in a copper frame with its number, so the boards are easy to tell apart.
  4. Background routing. Boards are routed in parallel worker threads, nearest to the centre of the view first; the page stays usable and frames fill in as boards finish.
  5. Only what is visible is drawn. Far away a board is drawn from a small cached image, closer up as traces and pads, and close up with pad names, so the view stays fast even with a million vertices.
  6. Verification. Every board is checked on its own (pads, clearance, traces, crossings, gender rule); the lists below show the findings with their board numbers.
Routing time grows faster than linearly with the size of one tree, so a single tree with many thousands of vertices takes a long time on its own board. Adjacency matrices are not offered here: a matrix of a million vertices would have 1012 entries.
